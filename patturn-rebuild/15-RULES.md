## 🔴 قوانین گردش نسخه (Version Control)

### R-001 — به‌روزرسانی قبل از هر تغییر 🔴 حذف‌نشدنی

> **قبل از هر تغییری** هوش مصنوعی باید از به‌روز بودن آخرین نسخه اطمینان حاصل کند.

```
قبل از شروع هر نوبت کاری یا هر تغییر:
  1. git status                  ← ببین چه چیزی dirty است
  2. git pull --ff-only           ← آخرین نسخهٔ شاخه را بگیر (بدون merge غیرضروری)
  3. اگر pull شکست خورد → ابتدا conflict را حل کن، بعد تغییر بده
  4. اگر pull ممکن نبود → به کاربر اطلاع بده و ادامه نده
```

**چرا:** جلوگیری از کار روی کد کهنه، conflictهای بزرگ و از دست رفتن تغییرات دیگران.

---

### R-002 — کامیت و پوش مستقل فارسی پس از تغییر هر فایل 🔴 حذف‌نشدنی

> بعد از تغییر **هر فایل**، همان فایل باید جداگانه کامیت و بلافاصله روی شاخهٔ فعال پوش شود؛ جمع‌کردن چند فایل در یک کامیت ممنوع است.

1. قبل از تغییر هر فایل، `git status` و `git pull --ff-only`؛ شکست pull مانع ادامه است.
2. ویرایش و بررسی همان فایل؛ `git add -- <path>` و کامیت تک‌فایلی با توضیح کامل فارسی طبق R-003.
3. `git push origin <شاخهٔ فعال>` بلافاصله بعد از همان کامیت؛ سپس فایل بعدی.
4. فایل تولیدشده (مانند handbook) و هر metadata نسخه نیز فایل مستقل است و کامیت/پوش مستقل دارد.
5. برای تغییر چندفایلی وابسته، کامیت‌های میانی با `[skip ci]` و توضیح «میانی؛ آمادهٔ انتشار نیست» مشخص شوند؛ ادعای عبور آزمون یکپارچه برای آن‌ها ممنوع است. آخرین کامیت بدون skip باید تمام تست‌ها و ساخت/انتشار همان HEAD را اجرا کند.
6. R-018 و R-019 برای **هر مجموعهٔ سازگار و تکمیل‌شدهٔ تحویل** اجرا می‌شوند؛ افزایش چند metadata در کامیت‌های تک‌فایلی انجام می‌شود. کامیت میانیِ ناسازگار نباید فایل نصب/آپدیت منتشر کند. این استثنا فقط ترتیب فنی تحویل است، نه حذف الزام نسخه/انتشار.
7. در شکست push، به‌جای رفتن به فایل بعدی ابتدا خطا رفع یا مانع صریحاً اعلام شود؛ هیچ تغییر کاربر پاک نشود.

**چرا:** درخواست صریح کاربر برای ردگیری مستقل هر فایل و حفظ توضیح کامل؛ قابل‌ساخت بودن و انتشار فقط برای HEAD نهایی مجموعه تضمین می‌شود.

---

### R-003 — پیام کامیت فارسی با توضیح کامل 🔴

قالب اجباری پیام کامیت (توضیح کامل، نه مختصر):

```
<فعل فارسی + شرح مشخص نتیجهٔ تغییر همان فایل> [skip ci فقط برای کامیت میانی]

- فایل و بخش تغییرکرده: مسیر و اجزای دقیق تغییر.
- علت و هدف: درخواست کاربر/شناسهٔ نیازمندی و مشکل قبلی.
- جزئیات رفتار یا قرارداد جدید: دامنه، ورودی/خروجی، وابستگی‌ها و سازگاری.
- بررسی و آزمون: فرمان واقعاً اجراشده و نتیجه؛ اگر یکپارچه اجرا نشده صریح گفته شود.
- محدودیت‌ها و ادامه: موارد ناتمام، اثر امنیتی/داده‌ای و وضعیت نسخه/انتشار.
```

**ممنوع:** `fix`، `update`، `wip`، `misc`، عنوان مبهم یا بدنهٔ کوتاه فاقد علت/جزئیات/آزمون؛ نسبت‌دادن نتیجهٔ آزمون اجرا‌نشده به فایل.

کامیت پایانی مجموعه، علاوه بر توضیح کامل همان فایل، نسخه، نتیجهٔ کل آزمون‌ها و وضعیت واقعی CI/Release را ثبت کند؛ موفقیت انتشار آینده از قبل ادعا نشود.

---

### R-004 — کار فقط روی شاخهٔ فعال 🔴

- شاخهٔ جاری session را تغییر نده، شاخهٔ جدید نساز (مگر کاربر صریحاً بخواهد).
- push فقط به شاخهٔ فعال: `git push origin <branch>` — هرگز به `main` یا شاخهٔ دیگر مستقیم پوش نکن.
- merge/pull request فقط با اجازهٔ کاربر.

### R-005 — بدون کامیت فایل‌های حساس 🔴

- `.env`، کلیدها، توکن‌ها، رمزها، اطلاعات شخصی کاربر هرگز کامیت نشوند.
- خروجی‌های build، نصب‌کننده‌ها و دیتاست‌های بزرگ در Git نروند (مسیرهای `.gitignore`).
- اگر سهواً فایل حساس کامیت شد → فوری: حذف از تاریخچه + اطلاع به کاربر.

## 🧮 قوانین هندسی و محصول

### R-006 — واحد میلی‌متر 🔴 حذف‌نشدنی

همهٔ محاسبات داخلی با `number` در میلی‌متر. تبدیل اینچ/سانتی‌متر فقط در لایهٔ نمایش. هیچ فایل خروجی بدون واحد صریح mm تولید نشود.

### R-007 — پروژه = پارامتر، نه مش 🔴 حذف‌نشدنی

فایل پروژه فقط JSON پارامترهاست (`schemaVersion` دارد). مش همیشه از پارامتر بازتولید میشود. ذخیرهٔ مش به‌عنوان منبع حقیقت ممنوع است.

### R-008 — قطعیت هندسی 🔴 حذف‌نشدنی

همان پارامترها → همیشه همان مش (هش یکسان). `Math.random()` بدون seed ممنوع. نتایج تست‌های طلایی قابل تغییر با «به‌بودی» نیستند؛ فقط با اصلاح باگ.

### R-009 — واترتایت بودن خروجی 🔴 حذف‌نشدنی

قبل از هر export STL: بررسی لبهٔ باز، نرمال، خودتقاطع، Euler. اگر نقص بود → ترمیم خودکار یا پیام فارسی به کاربر؛ خروجی خراب هرگز تحویل داده نشود.

## 🚀 قوانین نسخه و فایل‌های قابل‌دانلود

### R-018 — افزایش نسخه بعد از هر تغییر 🔴 فعال

> بعد از هر واحد تغییر تکمیل‌شده، نسخهٔ برنامه متناسب با تغییر افزایش یابد؛ تغییر بدون افزایش نسخه تحویل نشود.

- از SemVer استفاده شود: اصلاح خطا/مستندات/تست/CI → patch، قابلیت سازگار جدید → minor، تغییر ناسازگار قرارداد → major.
- نسخهٔ ریشه، workspaceها، وابستگی‌های داخلی، lockfile، Tauri و Cargo هم‌زمان هماهنگ و CHANGELOG فارسی ثبت شوند.
- افزایش نسخه جزئی از همان کامیت تغییر است؛ نسخهٔ منتشرشده بازنویسی یا برای محتوای متفاوت دوباره استفاده نشود.
- چک: `npm run release:check` و مقایسهٔ نسخه با والد/مبدأ تغییر، پیش از کامیت/انتشار.

### R-019 — انتشار فایل نصب و آپدیت پس از هر تغییر 🔴 فعال

> پس از هر تغییر تکمیل‌شده و افزایش نسخه، فایل‌های نصب و به‌روزرسانی نسخهٔ وب و ویندوز در Release قابل‌دانلود منتشر شوند.

- ساخت و آزمون‌ها باید برای همان commit موفق باشند؛ فایل وب ZIP، نصب‌کنندهٔ ویندوز، هش SHA-256 و راهنمای نصب/ارتقای دستی ارائه و لینک واقعی Release اعلام شود.
- نصب‌کنندهٔ همان نسخه می‌تواند فایل ارتقای دستی ویندوز و ZIP وب فایل جایگزینی نسخهٔ وب باشد؛ این‌ها «آپدیت خودکار امضاشده» نامیده نشوند.
- تا تکمیل Release Gate و شواهد نصب/حذف، آفلاین و آزمون فیزیکی، خروجی فقط با برچسب روشن **آزمایشی / prerelease / بدون امضا** منتشر شود، نه انتشار نهایی تأییدشده.
- انتشار نهایی یا آپدیت خودکار نباید گیت شواهد/امضا را دور بزند؛ کلید خصوصی، رمز یا توکن در مخزن/چت ثبت نشود.
- در خطای ساخت/آزمون/دسترسی، فایل قدیمی به نام نسخهٔ جدید منتشر نشود؛ مانع و وضعیت انتشار صریحاً اعلام و فقط پس از رفع آن انتشار تکمیل شود.
- چک: نتیجهٔ CI همان commit، فهرست assetهای Release و هش‌ها؛ تحویل بدون فایل/لینک با ادعای «منتشر شد» ممنوع است.
